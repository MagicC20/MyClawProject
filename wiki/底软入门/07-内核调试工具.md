# 07. 内核调试工具

> 底软工程师 50% 的时间在调试。  
> 这一章把"看到内核在想什么"的工具都讲一遍。

---

## printk 与 dmesg

最基础也最常用。

### 最佳实践

```c
// 🔴 内核态

// ❌ 反模式：到处 printk，干扰日志
printk("read called\n");
printk("i = %d\n", i);

// ✅ 好习惯：用 pr_* 宏 + 有意义的标签
pr_info("mychardev: read %zu bytes from user\n", count);

// ✅ 调试期间用动态调试
pr_debug("internal state: i=%d buf=%p\n", i, buf);
// 默认不输出，通过动态调试开关启用
```

### 控制 printk 日志级别

```bash
# 查看当前控制台日志级别
$ cat /proc/sys/kernel/printk
4       4       1       7
│       │       │       └─ 最大级别
│       │       └─────── 默认级别（启动时）
│       └─────────────── 当前控制台级别
└─────────────────────── 当前消息级别

# 临时改：只显示 ERR 及以上
$ sudo echo 3 > /proc/sys/kernel/printk

# 或者在内核命令行加：loglevel=3
```

### 动态调试（Dynamic Debug）

`pr_debug` / `dev_dbg` 默认编译成空操作（不输出）。需要时打开：

```bash
# 启用某个文件的所有 dev_dbg
$ sudo echo "file mychardev.c +p" > /sys/kernel/debug/dynamic_debug/control

# 启用某个函数的 pr_debug
$ sudo echo "func mychardev_read +p" > /sys/kernel/debug/dynamic_debug/control

# 查看当前规则
$ sudo cat /sys/kernel/debug/dynamic_debug/control | head
```

⚠️ 需要内核配置 `CONFIG_DYNAMIC_DEBUG=y`。

## GDB：源码级调试

### 用 GDB 调试用户态程序（你应该熟）

```bash
$ gdb ./test_ioctl
(gdb) break main
(gdb) run
(gdb) next
```

### 用 GDB 调试内核模块

内核模块不能用普通 `gdb ./hello.ko` 启动。需要让内核跑起来后 attach。

#### 方法 1：用 kgdb（需要两台机器或 QEMU）

```bash
# 启动时加内核参数
kgdboc=ttyS0,115200 kgdbwait

# 在另一台机器（或 minicom）连进来：
(gdb) target remote /dev/ttyS0
(gdb) set print pretty on
```

#### 方法 2：用 QEMU + GDB stub（推荐，单机就能调试）

```bash
# 启动 QEMU 时打开 GDB stub
$ qemu-system-x86_64 -kernel bzImage -append "nokaslr" -S -gdb tcp::1234
                                                ↑    ↑
                                                启动时停止  GDB 端口

# 另一个终端
$ gdb vmlinux
(gdb) target remote :1234
(gdb) b mychardev_read
(gdb) c   # continue
# QEMU 这时会启动内核
# 加载模块后触发 read，会停在断点
```

#### 方法 3：加载符号到运行中的内核

```bash
# 让内核能加载符号（需要 root）
$ sudo echo 0 > /proc/sys/kernel/kptr_restrict

# GDB 加载 vmlinux 符号
$ gdb /usr/lib/debug/boot/vmlinux-$(uname -r)
(gdb) add-symbol-file /path/to/mychardev.ko 0xffffffffc0000000
                                        ↑ 模块加载地址（从 /proc/modules 查）
(gdb) b mychardev_read
(gdb) c
```

⚠️ 这种方法不能下断点后单步（因为没有 ptrace 内核模块的能力），但能看函数和变量。

## strace：跟踪用户态系统调用

调试"应用调用驱动"问题时，先用 strace 看应用到底下了什么命令：

```bash
$ strace -e trace=open,read,write,ioctl ./test_ioctl
openat(AT_FDCWD, "/dev/mychardev", O_RDWR) = 3
ioctl(3, _IOR(0x6d, 1, 4), 0x7ffc12345678) = 0
ioctl(3, _IO(0x6d, 2))                 = 0
+++ exited with 0 +++
```

这把 ioctl 命令完整显示出来了（magic=0x6d='m', nr=1, size=4）。

## ftrace：函数跟踪器

内核自带，不需要额外工具。

### 跟踪特定函数

```bash
# 查看可用的跟踪器
$ sudo cat /sys/kernel/debug/tracing/available_tracers
function function_graph blk mmiotrace ...

# 启用 function 跟踪器
$ sudo echo function > /sys/kernel/debug/tracing/current_tracer

# 设置要跟踪的函数
$ sudo echo "mychardev_open" > /sys/kernel/debug/tracing/set_ftrace_filter
$ sudo echo "mychardev_read" >> /sys/kernel/debug/tracing/set_ftrace_filter

# 启用
$ sudo echo 1 > /sys/kernel/debug/tracing/tracing_on

# 应用操作设备
$ cat /dev/mychardev

# 查看 trace
$ sudo cat /sys/kernel/debug/tracing/trace
# tracer: function
#
# entries-in-buffer/entries-written: 4/4   #P:8
#
#                              _-----=> irqs-off
#                             / _----=> need-resched
#                            | / _---=> hardirq/softirq
#                            || / _--=> preempt-depth
#                            ||| /     delay
#           TASK-PID    CPU#  ||||    TIMESTAMP  FUNCTION
#              | |       |   ||||       |         |
          <idle>-0     [000] d..3   123.456789: mychardev_open <-do_dentry_open
          <idle>-0     [000] d..3   123.456801: mychardev_read <-vfs_read

# 关闭
$ sudo echo 0 > /sys/kernel/debug/tracing/tracing_on
```

### function_graph：看函数调用图

```bash
$ sudo echo function_graph > /sys/kernel/debug/tracing/current_tracer
$ sudo echo mychardev_read > /sys/kernel/debug/tracing/set_graph_function
$ sudo echo 1 > /sys/kernel/debug/tracing/tracing_on

$ sudo cat /sys/kernel/debug/tracing/trace
 0)               |  mychardev_read() {
 0)               |    copy_to_user() {
 0)   0.123 us    |      _copy_to_user();
 0)   0.456 us    |    }
 0)   1.234 us    |  }
```

## perf：性能分析

### 性能计数器

```bash
# 记录 10 秒内的所有 CPU 性能事件
$ sudo perf record -a -g sleep 10
$ sudo perf report
# 火焰图视图
```

### 看内核热点

```bash
# 查看某个内核函数被调用次数
$ sudo perf stat -e 'syscalls:sys_enter_ioctl' sleep 5
 Performance counter stats for 'system wide':
        12345  syscalls:sys_enter_ioctl

       5.001234  seconds time elapsed
```

## KASAN：内核内存错误检测器

类似用户态的 AddressSanitizer，能抓到：

- 越界访问
- Use-after-free
- Double-free

```bash
# 内核配置
CONFIG_KASAN=y
CONFIG_KASAN_INLINE=y

# 触发 bug 后会看到类似输出
$ sudo dmesg | tail
==================================================================
BUG: KASAN: slab-out-of-bounds in mychardev_read+0x23/0x80
Read of size 8 at addr ffff888012345678
...
```

## KMEMLEAK：内存泄漏检测

```bash
# 启用
$ sudo echo 1 > /sys/kernel/debug/kmemleak/enable

# 让它扫一遍（要等几分钟）
$ sudo echo scan > /sys/kernel/debug/kmemleak/kmemleak

# 查看泄漏报告
$ sudo cat /sys/kernel/debug/kmemleak/kmemleak
```

## Oops / Panic 分析

当内核 panic 时，屏幕会刷一堆信息：

```
BUG: unable to handle kernel NULL pointer dereference at 0000000000000010
IP: mychardev_read+0x23/0x80
...
Call Trace:
 <TASK>
 mychardev_read+0x23/0x80
 ? __pfx_mychardev_read+0x10/0x10
 vfs_read+0xa4/0x1f0
 ksys_read+0x67/0xe0
 __x64_sys_read+0x1a/0x20
 do_syscall_64+0x59/0xc0
 entry_SYSCALL_64_after_hwframe+0x44/0xae
 </TASK>
```

关键信息提取：
1. **错误类型**：`NULL pointer dereference` / `kernel BUG` / `stack overflow`
2. **出错的 IP**（指令地址）：`mychardev_read+0x23/0x80`
3. **Call Trace**：调用栈，从下往上看
4. **寄存器值**：`RIP`、`RSP` 等
5. **Tainted flags**：内核是否被污染

### 用 addr2line 定位行号

```bash
# 你有未 strip 的 .ko
$ addr2line -e mychardev.ko 0x23
/home/you/mychardev.c:67
```

## 实战：用 printk + GDB 排查 NULL 指针

```c
// 🔴 内核态 — 一个有 bug 的驱动
static ssize_t mychardev_read(struct file *filp, char __user *buf,
                              size_t count, loff_t *ppos)
{
    struct my_device *dev = filp->private_data;  // ← 没检查就解引用
    
    int *status = dev->status_reg;  // ← 如果 dev 为 NULL，这里 panic
    ...
}
```

排查步骤：

```bash
# 1. 触发 bug
$ cat /dev/mychardev
# 系统 panic，屏幕显示 NULL pointer dereference in mychardev_read+0x12

# 2. 看 Call Trace
# vfs_read → mychardev_read → kernel BUG

# 3. 检查代码
# 发现 open 时没设置 filp->private_data，所以 dev 是 NULL

# 4. 修复
static int mychardev_open(struct inode *inode, struct file *filp)
{
    filp->private_data = &global_my_device;  // ← 加上这一行
    return 0;
}
```

## 调试速查表

| 场景 | 推荐工具 |
|---|---|
| 快速看运行情况 | `dmesg` + `printk` |
| 用户态调用是否到驱动 | `strace` |
| 函数是否被调用 | `ftrace` |
| 函数调用栈 | `ftrace function_graph` |
| 性能瓶颈 | `perf` + `flamegraph` |
| 内存越界/UAF | `KASAN` |
| 内存泄漏 | `kmemleak` |
| 内核 panic | dmesg + `addr2line` + GDB 源码对照 |
| 单步调试内核 | QEMU + GDB stub |
