# 13. AI 芯片架构基础

> 这一章跳出"驱动"本身，从硬件角度理解你将要为之写驱动的设备。  
> 理解了硬件，软件就是顺势而为。

---

## AI 芯片和传统 CPU 的本质区别

| 维度 | CPU | AI 芯片（NPU/DSA） |
|---|---|---|
| 核心目标 | 通用计算 | 特定计算模式（矩阵乘、卷积）|
| 算力 | 几十 GFLOPS | 几十 ~ 几百 TOPS |
| 内存 | 大 cache + DRAM | 容量小但带宽极高（SRAM）|
| 编程模型 | 指令流 | 算子/计算图 |
| 适合任务 | 通用代码 | 矩阵乘、卷积、注意力 |

**核心理念**：AI 芯片用专用电路（PE Array / Tensor Unit）加速特定计算模式，代价是灵活性下降。

## AI 芯片的核心组成

```
┌──────────────────────────────────────────────┐
│                Host Interface                 │  ← PCIe / AXI
├──────────────────────────────────────────────┤
│  ┌─────────────┐    ┌─────────────┐          │
│  │  DMA 引擎   │    │  DMA 引擎   │          │  ← 多个通道
│  └─────────────┘    └─────────────┘          │
├──────────────────────────────────────────────┤
│  ┌──────────────────────────────────────┐    │
│  │       计算单元（PE Array）            │    │  ← 矩阵乘的硬件实现
│  │       128×128 矩阵乘 1 cycle          │    │
│  └──────────────────────────────────────┘    │
├──────────────────────────────────────────────┤
│  ┌────────────┐   ┌────────────┐             │
│  │   SRAM     │   │   SRAM     │             │  ← 片上缓存，带宽极高
│  │  (输入)    │   │  (输出)    │             │
│  └────────────┘   └────────────┘             │
├──────────────────────────────────────────────┤
│  ┌────────────┐   ┌────────────┐             │
│  │  调度器    │   │  控制器    │             │  ← 任务调度、状态机
│  └────────────┘   └────────────┘             │
└──────────────────────────────────────────────┘
```

各部分职责：

| 模块 | 干什么 |
|---|---|
| Host Interface | 接收主机的命令和数据（PCIe、SoC 总线）|
| DMA 引擎 | 在主机内存和芯片 SRAM 之间搬数据 |
| 计算单元（PE Array）| 执行实际的矩阵乘/卷积运算 |
| 片上 SRAM | 高速缓存，存放当前计算的 tile |
| 调度器 | 决定计算单元和 DMA 怎么配合 |

## 计算模型：算子 → 计算图

### 算子（Operator）

AI 计算被分解成一个个基本操作（算子）：

```
矩阵乘：C = A × B
卷积：Y = conv(X, W)
激活：Y = relu(X)
归一化：Y = layernorm(X)
```

每个算子在芯片上有对应实现（可能是专用电路，也可能是软件模拟）。

### 计算图（Graph）

一个神经网络模型被表示成算子的依赖图：

```
输入 → [MatMul] → [Bias] → [ReLU] → [MatMul] → [Softmax] → 输出
         ↓          ↓        ↓         ↓
       A × W      + b       max(0)    A × W      exp/sum
```

驱动通常**不**直接构造计算图（这是编译器/SDK 的活）。驱动只负责：
- 接收一个已经编排好的"任务"
- 配置硬件
- 启动执行
- 等中断

## Tensor 数据布局

数据怎么在内存里排布，直接影响硬件访问效率。

### NCHW vs NHWC

4D Tensor (N=batch, C=channel, H=height, W=width)：

```
NCHW: 先按 W，再 H，再 C，最后 N  ← PyTorch 默认
NHWC: 先按 W，再 H，再 C，最后 N（实际叫 HWCN 顺序排）← TensorFlow 默认
```

```c
// 同一个 2×3×2×2 的 Tensor，NCHW 内存布局：
// [N0C0H0W0, N0C0H0W1, N0C0H1W0, N0C0H1W1,
//  N0C1H0W0, N0C1H0W1, ...]
```

为什么重要：
- 硬件的 PE 阵列按特定模式访问数据
- 布局不匹配 = 性能下降 2~10 倍
- 驱动和 SDK 需要协商数据布局

### 块布局（Tile Layout）

芯片内部按 tile 工作，把 Tensor 切成小块：

```
┌────────────────┐
│  Tile 0 │  Tile 1  │   ← 按行切
├────────────────┤
│  Tile 2 │  Tile 3  │
└────────────────┘
```

每个 tile 装进芯片 SRAM，PE 阵列处理 tile，处理完写回主机内存。

## 芯片上的内存层次

```
主机 DRAM（GB 级，~100 GB/s 带宽）
   ↑
PCIe / 总线（瓶颈）
   ↓
芯片 SRAM（MB 级，~TB/s 带宽）
   ↓
PE 寄存器（KB 级，~10 TB/s）
```

**关键洞察**：AI 芯片算力极强，但数据搬运能力可能跟不上。如果驱动调度不当，硬件会"饿死"。

驱动的作用：
- 把数据搬到合适的位置（DMA）
- 让 PE 在等数据的时间做别的（流水线）
- 减少数据搬运（计算融合、算子合并）

## 芯片 Bring-up 流程

一个 AI 芯片从流片回来到能跑模型，要经历几个阶段：

```
1. Silicon Bring-up（硬件验证）
   - 给芯片上电
   - 用 JTAG 调试器连芯片
   - 测试基本寄存器读写
   - 由硬件工程师主导

2. Boot ROM 验证
   - Boot ROM 是芯片出厂固化的第一段代码
   - 测试它能初始化最基本的硬件
   - 由硬件 + 固件工程师主导

3. Bootloader（U-Boot / 自研）
   - 从 Flash 加载固件到 SRAM
   - 初始化 DRAM、DDR
   - 由固件工程师主导

4. Linux 内核启动
   - Bootloader 加载 kernel + dtb + rootfs
   - 内核初始化驱动
   - 由底软工程师主导

5. 驱动 bring-up
   - 加载芯片驱动
   - 验证基本 IO（读寄存器、写寄存器、看中断）
   - 验证 DMA（搬一帧数据，看对不对）
   - 验证计算（跑一个小模型，对结果）
   - 由底软工程师主导

6. 框架集成
   - ONNX Runtime / PyTorch 自定义算子适配
   - 模型转换（量化、编译）
   - 端到端跑通 ResNet
   - 由 SDK + 算法工程师主导
```

作为底软工程师，你的工作集中在 **5. 驱动 bring-up**。

## 驱动 bring-up 的典型工作流

### 第一天：确认硬件可达

```c
// 1. 读版本寄存器
u32 version = ioread32(priv->regs + 0x0);
pr_info("chip version: 0x%x\n", version);

// 2. 读 ID 寄存器
u32 chip_id = ioread32(priv->regs + 0x4);

// 3. 检查和预期是否一致
if (version != EXPECTED_VERSION) {
    dev_err(dev, "wrong chip version: 0x%x\n", version);
    return -ENODEV;
}
```

### 第二天：验证中断

```c
// 在 probe 里模拟触发一次中断
iowrite32(0x1, priv->regs + 0x100);  // 写命令寄存器触发软中断

// 然后看 ISR 有没有被调用
// 用 pr_info 或 ftrace 看
```

### 第三天：验证 DMA

```c
// 分配一致性 DMA 缓冲区
void *buf = dma_alloc_coherent(dev, 4096, &dma, GFP_KERNEL);

// 填充测试模式
memset(buf, 0xAA, 4096);

// 启动 DMA：把 buf 搬到芯片 SRAM
iowrite32(dma, priv->regs + 0x300);
iowrite32(4096, priv->regs + 0x304);
iowrite32(0x1, priv->regs + 0x308);  // 启动

// 等中断
// 读回 SRAM 内容，对比
```

### 第四天：跑最小计算

```c
// 1. 上传一个小模型（手写汇编指令）
// 2. 启动计算
// 3. 等完成中断
// 4. 读结果
// 5. 和 CPU 算的结果对比
```

## 寄存器手册怎么看

芯片公司会给一份几百到几千页的寄存器手册（Register Specification），结构：

```
第 1 章：Overview
第 2 章：Block Diagram（芯片框图）
第 3 章：Address Map
  → 每个模块的基址
第 4 章：Interrupt Map
  → 每个中断的来源
第 5 章：Register Description（最重要）
  → 每个寄存器的位定义
第 6 章：Programming Guide（如果有的话）
  → 推荐的初始化/操作流程
```

### 寄存器描述的典型格式

```
寄存器名：DMA_CTRL
偏移地址：0x300
复位值：0x0000_0000

位域：
  [31:16]  Reserved
  [15:8]   BURST_SIZE    - 突发传输大小（0=8, 1=16, 2=32 ...）
  [7:4]   CHANNEL_SEL    - DMA 通道选择
  [3]     INT_EN         - 完成中断使能
  [2:1]   DIR            - 传输方向（00=Mem->Mem, 01=Mem->Dev, 10=Dev->Mem）
  [0]     START          - 写 1 启动 DMA

说明：
  写此寄存器启动 DMA，传输完成后如果 INT_EN=1 则产生中断。
  BUSY 位（只读，偏移 0x304 bit 0）显示当前是否在传输中。
```

### 读手册的技巧

1. **先看 Programming Guide**：如果有，优先看，比直接啃寄存器快
2. **找 Address Map**：确定你要的寄存器在哪个基址
3. **找例子代码**：很多手册会附伪代码或示例
4. **问**：硬件工程师永远是最好的资源

## 软件栈全景

```
┌────────────────────────────────────────┐
│       AI 框架（PyTorch / TF）           │
├────────────────────────────────────────┤
│       ONNX Runtime / 编译器             │  ← 把模型转成芯片指令
├────────────────────────────────────────┤
│       Runtime SDK（libmychip.so）      │  ← 用户态库
│         ↑                              │
│   /dev/mychip  (ioctl, mmap)           │  ← 驱动接口
│         ↓                              │
│       内核驱动                          │  ← 你写的
│         ↓                              │
│       固件（Firmware, optional）        │
│         ↓                              │
│       芯片硬件                          │
└────────────────────────────────────────┘
```

底软工程师通常工作在下半部分，但需要**理解**上面所有的接口形态。
